# Update — April 2, 2026

## Customer Management Fixes

Based on the feedback received, the following issues with customer creation, editing, and deletion have been identified and resolved:

### 1. Delete Button — Fixed
**Issue:** The delete button was not working for staff and accountant users.  
**Root Cause:** The backend delete endpoint was restricted to `account_owner` role only, which blocked staff and accountant users from deleting customers. The frontend silently swallowed the 403 error.  
**Fix:** Updated the role permission on the delete endpoint to allow all authenticated roles (staff, accountant, account_owner, super_admin) to delete customers. Tenant-level isolation still ensures users can only delete customers within their own account.

### 2. Customer Creation — Fixed
**Issue:** Creating a customer sometimes worked and sometimes didn't.  
**Root Cause:** When optional fields like email were left empty, the frontend sent empty strings (`""`) to the backend. The Zod validation schema rejected empty strings because `""` is not a valid email format, not `null`, and not `undefined`. This caused intermittent 400 validation errors — it worked when email was filled in, but failed when left blank.  
**Fix:** Added an `emptyToNull` transform in the backend validation schema that automatically converts empty strings to `null` before validation runs. This means all optional fields now gracefully handle empty inputs.

### 3. Edit Customer — Fixed
**Issue:** Editing a customer was not working at all.  
**Root Cause:** The frontend was sending a `PATCH` request to update customers, but the backend only had a `PUT` route defined. The `PATCH` request returned a 404 (route not found).  
**Fix:** Added a `PATCH` route handler on the backend that mirrors the existing `PUT` handler, so both HTTP methods are now supported for updating customers.

### 4. Phone Number — Digits Only Validation Added
**Issue:** The phone field accepted any characters (letters, symbols, etc.).  
**Fix:**  
- **Frontend:** Added input restriction so only numeric digits can be typed into the phone field. Non-numeric characters are blocked at the keyboard level.  
- **Backend:** Added a regex validation rule (`/^\d+$/`) to the phone field in the Zod schema, ensuring only numeric values are accepted. If a non-numeric phone number is submitted, the API returns a clear validation error: "Phone must contain only numbers."
